# 前端升级笔记:从"能跑的入门项目"到"中型前端工程"

> 本文件记录用户管理系统**前端方向**的升级规划与执行过程。
> 起因:后端已由 Agent 驱动重构(分层/异常兜底/ThreadLocal 鉴权/VO 隔离),工程素养中等以上;
> 前端却停留在"全 JS + 326 行单文件 + 无懒加载"的入门水准,**前后端落差是最大露馅点**。
> 目标:用 3 个深度单点 + 减法,让前端配得上后端,简历可信度对齐"中级前端"。

---

## 一、现状评估:为什么"看上去像新手"

### 1.1 后端已具备的工程信号(基线,别被前端拖后腿)

| 信号 | 证据 |
| :--- | :--- |
| 分层清晰 | controller/service/repository,UserController 仅 90 行,业务全在 UserService |
| ThreadLocal 鉴权 | UserContext + AuthInterceptor.afterCompletion 清空防线程串号 |
| 异常兜底三层 | GlobalExceptionHandler 接 BizException / 404 / 500,500 不泄露内部细节 |
| VO 隔离 password | UserVO.from() 唯一转换入口 + User 实体 @JsonProperty(WRITE_ONLY) 双保险 |
| 泛型 Result | Result<T> 统一信封,呼应前端应有 BizResult<T> 类型 |

### 1.2 前端的关键短板(露馅点)

| 维度 | 后端 | 前端现状 | 落差 |
| :--- | :--- | :--- | :--- |
| 类型 | Java 强类型 + 泛型 | 全 JS,仅 1 个孤儿 .ts(request.ts) | **大** |
| 代码组织 | controller/service/repository 分层 | UserManage.vue 326 行 CRUD+表单+搜索全堆一起 | **大** |
| 路由加载 | 不适用 | 全部同步 import,无懒加载 | **大** |
| 异常兜底 | GlobalExceptionHandler 三层 | request.ts 拦截器有,但组件层 try/catch 套娃 | 中 |
| 取当前用户 | ThreadLocal 优雅 | router 里 if/else 套 4 个 meta | 中 |

### 1.3 新手项目的最大陷阱:靠堆功能数量假装成熟

新手容易踩的坑:加 10 个 CRUD 页面、堆 5 个图表,以为"功能多=成熟"。
面试官不看数量,看**单点深度**。判断维度:

1. **单点深度 > 功能数量**:一个 ECharts 做到"懒加载 + onUnmounted 释放 + resize 监听移除 + TS 类型化 + mock 兜底 + 数据补零" = 中级信号;堆 5 个图但漏 dispose = 仍新手。
2. **工程化痕迹**:TS、ESLint(已有)、路由懒加载、环境变量分层(已有)、单元测试、构建产物分析。
3. **代码组织约定**:组件 200 行内、composable 抽到底、目录约定(api/types/composables/views/components)。

## 二、升级策略:3 个深度单点 + 减法

不做 5 个方向铺开,聚焦 3 个单点,每个做到能讲透。

| 优先级 | 单点 | 为什么是它 | 深度信号 |
| :--- | :--- | :--- | :--- |
| P0 | TypeScript 全面接入 + 类型化 API 层 | 消除"全 JS"最大露馅点,面试硬门槛 | 类型推导、DTO/VO 概念 |
| P0 | ECharts 看板 + 真实数据 | 视觉冲击 + 简历宣称技能落地 | 生命周期、内存泄漏、数据分布 |
| P1 | UserManage 拆分 + composable 抽到底 | 消除"326 行单文件"露馅点 | 组件拆分、hook 封装 |

**减法清单**(砍掉凑数功能,不是加法越多越好):
- 首页"快捷入口"面板 → 砍,自己都不点
- 首页"系统信息"面板 → 砍,凑数
- 全 JS → 改 TS
- 全同步路由 import → 改懒加载

**顺手做**(不单独立项,在做主任务时附带):
- 路由懒加载 `() => import()`
- keep-alive 缓存列表页
- AbortController 搜索竞态取消

## 三、执行顺序与决策依据

```
任务一:TS api 层类型化          (P0,有完成时刻,最高价值)
    ↓
任务二:造数据(SQL 脚本)          (后端独立任务,不阻塞前端)
    ↓
任务三:首页 ECharts 改造(2 张图)   (配合新数据立即有视觉冲击)
    ↓
任务四:TS composable + store 类型化 (巩固深度)
    ↓
任务五:dashboard 独立页(剩余图表)
    ↓
任务六:UserManage 拆分 + composable 抽离
```

**为什么 TS 排第一**:TS 是贯穿性改造,越早越值。api 层类型化后,IDE 智能提示能帮写 ECharts 数据交互,避免"用 JS 写完再回头加类型"的返工。

**为什么造数据排第二**:独立任务,不阻塞前端;且 ECharts 需要真实分布数据才好看,SQL 脚本先行。

## 四、任务一:TypeScript 接入(api 层优先)

### 4.1 思路

不追求一步到位全 TS,**渐进式策略**:
1. 先把 api 层类型化 → 简历亮点最高、IDE 智能提示立即生效
2. 再 composable/store(纯函数,迁移成本最低)
3. 最后组件层,允许 `as any` 过渡

### 4.2 新增文件

- `src/types/user.ts` —— 集中定义 UserVO、LoginVO、UserQuery、UpdatePayload
- `src/types/api.ts` —— 通用返回 `BizResult<T>`(对应后端 Result.java)
- `src/types/enums.ts` —— RoleEnum、StatusEnum(替代硬编码字符串)

### 4.3 关键设计

**BizResult<T>** 对应后端 `Result.java`:
```ts
interface BizResult<T> {
  code: number
  message: string
  data: T
}
```

**UserVO** 对应后端 `UserVO.java`,字面量联合类型比 number 安全:
```ts
interface UserVO {
  id: number
  username: string
  email: string
  name: string
  role: 'admin' | 'user'
  status: 0 | 1
  createdAt: string  // 后端格式化成字符串
}
```

### 4.4 任务分解

- 任务1.1:创建 `src/types/user.ts`,定义 UserVO(含功能扩展后的新字段) → 简单
- 任务1.2:创建 `src/types/api.ts`,定义 BizResult<T> → 简单
- 任务1.3:创建 `src/types/enums.ts`,RoleEnum/StatusEnum → 简单
- 任务1.4:`api/user.js` → `api/user.ts`,每个函数加返回类型 `Promise<BizResult<UserVO>>` → 中等
- 任务1.5:`request.ts` 的拦截器回调补类型(AxiosResponse<BizResult<any>>) → 简单

### 4.5 验收标准

- [ ] `src/types/` 目录下有 3 个类型文件
- [ ] `api/user.ts` 所有函数有返回类型,IDE 里 `res.data.` 能智能提示字段
- [ ] `request.ts` 拦截器有类型标注
- [ ] `npm run dev` 正常启动,功能无回归
- [ ] `tsconfig` 仍为 `strict: false`(初期不追求严格模式)

### 4.6 风险

- 学习曲线:先做 api 层(任务 1.1-1.4),熟练后再 composable/store
- 不要追求 100% TS,允许 `any` 过渡
- `strict: true` 别早开,会报一堆 null 检查错误

## 五、任务二:造数据(SQL 脚本方案)

### 5.1 思路

现状 DataInitializer.java 只插 15 条手写数据,`user1/user2/.../user14` 规律太强,面试官一眼看穿是测试数据。
真实项目数据特征:**分布要像**,不是数量多就行。

### 5.2 真实数据特征对照表

| 字段 | 真实感特征 | 现状差距 |
| :--- | :--- | :--- |
| username | 英文名+数字、带下划线、有长有短(mike_zhang23、lily88) | 全是 userN |
| email | 真实域名(@qq.com、@163.com、@gmail.com 混合) | 全是 @example.com |
| name | 中英文混合、有复姓、有少数民族名 | 全是"张三李四"排序 |
| createdAt | 近 1-2 年随机分布,周末少工作日多 | 全是 2024-01 固定日期 |
| role | admin 1-2 个,user 占 99% | 1 admin + 14 user |
| status | 90% 启用,10% 禁用 | 12 启用 3 禁用 |
| password | 不同用户不同密码(bcrypt 同密码同盐不同结果) | 全是 123456 |

### 5.3 方案选择:思路 B(SQL 脚本)

- 文件:`src/main/resources/data.sql`
- 数量:**1000 条**(数量够分页看出效果,趋势图有数据)
- 时间范围:**近 2 年随机分布**(折线图有看头)
- 触发:Spring Boot 启动自动执行(配 `spring.sql.init.mode=always`,但需注意与 DataInitializer 协调)
- **关键决策:与现有 DataInitializer 的协调**
  - 选项A:data.sql 执行 + DataInitializer 保留幂等逻辑(表空才插)
  - 选项B:废弃 DataInitializer,全部用 data.sql
  - **建议选项A**:DataInitializer 保留 admin/123456 种子账号(测试用),data.sql 补 1000 条假数据;两者幂等不冲突

### 5.4 生成方式

1000 条 INSERT 手写不现实,用工具生成:
- 用 Python/Node 脚本生成 data.sql(本地脚本,不入库)
- 或用 faker 在一次性 main 方法里生成打印 SQL,再贴进 data.sql

**注意**:email/username 要保证唯一(数据库有唯一约束),生成时要去重。

### 5.5 任务分解

- 任务2.1:写一个生成脚本(Python/Node),用 faker 生成 1000 条 INSERT 语句 → 中等
- 任务2.2:把生成的 SQL 写入 `src/main/resources/data.sql` → 简单
- 任务2.3:application.yml 配 `spring.sql.init.mode=always`(或协调 DataInitializer) → 简单
- 任务2.4:重启后端,验证 users 表有 1000 条数据,admin 账号可用 → 简单
- 任务2.5:验证分布(角色/状态/时间)符合真实感 → 简单

### 5.6 验收标准

- [ ] users 表有 1000 条假数据 + 1 条 admin 种子账号
- [ ] admin/123456 仍可登录
- [ ] 假数据 username 不重复、email 不重复
- [ ] createdAt 分布在近 2 年,周末少工作日多
- [ ] 角色分布:admin 1-2 个,user 998 个
- [ ] 状态分布:约 90% 启用,10% 禁用

### 5.7 风险

- 唯一约束冲突:生成脚本必须保证 username/email 唯一
- 与 DataInitializer 冲突:两者幂等逻辑要对齐
- 密码加密:SQL 脚本无法调用 bcrypt,需预先生成加密串贴进 SQL(或统一用 123456 的 bcrypt 值)

## 六、任务三:首页 ECharts 改造(B 方案)

### 6.1 思路

走 **B 方案:首页改造为看板首页**。SaaS 产品标准做法是"首页=数据看板",一登录看到核心指标,这是"成熟项目"信号。
对比堆 4 个图在老首页(A 方案):堆砌反而像新手堆功能。

### 6.2 首页新布局

```
┌─────────────────────────────────────┐
│  欢迎回来 hero 区(保留)              │
├─────────────────────────────────────┤
│  [用户总数] [活跃] [管理员] [年份]     │ ← 4 个数字卡片(保留)
├──────────────────┬──────────────────┤
│                  │                  │
│  近 30 天注册    │   角色分布       │ ← 2 个核心图
│  趋势折线图      │   饼图           │
│  (占 2/3 宽)     │  (占 1/3 宽)     │
└──────────────────┴──────────────────┘
(砍掉"快捷入口"和"系统信息"两个鸡肋面板)
```

### 6.3 新增文件

- `src/api/stats.js` —— 看板接口封装(独立于 user.js)
- `src/components/charts/RegisterTrendChart.vue` —— 折线图组件
- `src/components/charts/RolePieChart.vue` —— 饼图组件

### 6.4 接口契约(前后端对齐)

- `GET /api/stats/register-trend?days=30` → `[{date: "2026-08-01", count: 3}, ...]`
- `GET /api/stats/role-distribution` → `[{name: "admin", value: 1}, {name: "user", value: 998}]`

(后端聚合接口由 Agent 开发,本笔记仅记录前端契约)

### 6.5 任务分解

- 任务3.1:装依赖 `npm i echarts` → 简单
- 任务3.2:写 `api/stats.js`,封装 2 个接口 → 简单
- 任务3.3:写 RegisterTrendChart.vue,**重点遵守 onUnmounted 释放 + resize 监听移除**(已踩过坑) → 中等
- 任务3.4:写 RolePieChart.vue,同模式 → 中等
- 任务3.5:改造 HomeView.vue:砍快捷入口/系统信息,加 2 个图组件,2/3+1/3 布局 → 中等
- 任务3.6:`v-if` 守卫异步数据(项目约定) → 简单

### 6.6 关键约定(踩过的坑,必须遵守)

- **ECharts 实例必须在 onUnmounted 调 dispose()**,否则切换路由后实例堆积内存泄漏
- **window resize 监听必须在 onUnmounted 移除**,否则多次进入页面监听叠加
- **异步数据必须 v-if 守卫**,避免空数据 init 报错
- **y 轴 scale: true**,坐标轴自适应数据范围

### 6.7 验收标准

- [ ] 首页 hero 区 + 4 数字卡片保留
- [ ] 首页下方 2 个 ECharts 图正常渲染
- [ ] "快捷入口""系统信息"面板已移除
- [ ] 切换路由再回来,图正常(无内存泄漏)
- [ ] 浏览器 resize,图自适应
- [ ] 数据为空时不报错(v-if 守卫生效)

## 十一、升级后的项目全景

升级完成后,前端从"能跑的入门 CRUD"升级为:
**TypeScript 全程类型化 + ECharts 可视化看板 + 真实分布数据 + Composable 深度封装 + 路由懒加载/keep-alive 性能优化的中型前端工程**。

面试官翻代码时能看到:
- `src/types/` 类型定义(api 层泛型 BizResult<T>)
- `src/composables/` 通用 hook(useTable/useFormDialog)
- `src/components/charts/` 图表组件(生命周期管理规范)
- 路由懒加载 + keep-alive
- 1000 条真实分布数据(非 user1/user2 规律数据)

每一个都是面试常考点的实证,且后端不启动也能通过 mock 完整演示(兜底)。
**核心价值提升:前端配得上后端的工程素养,消除"前后端落差"这个最大露馅点。**
